## IronNestFCS Smart v1.2.0

### Physical fire settlement / 物理击发结算

- FirePlan completion is now driven by observed physical gunfire instead of assuming that the scheduled current gun must be the one that fired.
- Left and right gunfire are observed independently around the shared trigger event, with a short settlement window so simultaneous shots are reconciled together.
- If both guns physically fire, both matching FirePlans are consumed. If only one gun fires, only that plan is consumed and the remaining committed plan keeps its established execution order.
- A FirePlan ends at the observed shot; post-shot mechanical recovery remains owned by the persistent physical loading runtime.

- FirePlan 现在以“实际观察到哪门炮物理击发”为完成依据，不再假设调度中的 current 一定就是实际开火的炮。
- 共享扳机动作前后会分别观察左右炮，并保留一个很短的结算窗口，把近乎同时发生的双炮击发作为同一次物理事件处理。
- 如果左右炮都实际击发，就同时消费对应的两个 FirePlan；如果只有一门炮击发，只消费这一门的计划，剩余已提交计划继续保持既定执行顺序。
- FirePlan 在观察到实际击发时结束；击发后的机械复位仍由 Host 中的持久物理装填系统负责。

### Ready / Review / Arm handshake / 准备、确认与保险握手

- The five Review switches are now controlled by an independent physical-state reconciler. Task execution publishes gun-ready inputs; the controller continuously converges the shared switches to the required physical state.
- Review confirmation receives a short head start before arming, but arming no longer waits for all five switches to finish moving.
- Each gun operates only its own arming lever. A ready second gun may arm itself during the current shared-fire opportunity only when its target azimuth is effectively the same.
- The scheduler's `current / next` order remains authoritative for shared azimuth ownership; LocalReady does not reorder plans.

- 5 个 Review 确认开关现在由独立的物理状态控制器负责持续收敛；任务执行只发布左右炮的 ready 输入。
- Review 会在解除保险前获得一个短暂提前量，但不会等待 5 个开关全部完成动作后才开始解除保险。
- 每门炮只操作自己的保险。另一门已经准备好的炮，只有在本次共享击发机会中目标方位角基本一致时，才会由自己的流程解除自己的保险。
- 调度器原有的 `current / next` 顺序继续决定共享方位角执行权；LocalReady 不会重排 FirePlan。

### Two-gun task matching / 双炮任务匹配

- Planning now builds one side-effect-free Task × Gun eligibility matrix from a shared physical/loading snapshot before choosing assignments.
- A stateless two-gun matcher chooses the best non-conflicting assignment set and prioritizes filling currently available gun slots before soft tie-breaks.
- Shell compatibility and fixed-charge range sufficiency are treated as hard eligibility constraints.
- The game ballistic calculator is invoked only after a Task × Gun assignment has been selected, preventing rejected alternatives from producing extra firing-solution stickers.
- If a selected edge fails ballistic/elevation materialization, only that edge is excluded and the remaining candidates can be matched again without partially admitting the batch.

- 规划现在先基于同一个左右炮物理/装填快照建立无副作用的 Task × Gun 资格矩阵，再决定任务分配。
- 新的无状态双炮 Matcher 会从合法组合中选择互不冲突的最佳分配，并优先尽可能填满当前可用炮位。
- 弹种兼容和固定装药能否覆盖射程属于硬资格条件。
- 只有最终选中的 Task × Gun 组合才会调用游戏弹道计算器，未选中的候选不再额外生成射击解算贴纸。
- 如果最终选中的某条边在弹道/仰角实体化阶段失败，只排除这条边并重新匹配；在整批实体化成功前不会半途向 Executor 提交计划。

### Recovery-aware Pending dispatch / 面向物理恢复状态的 Pending 调度

- Pending tasks no longer stall when one free gun slot is still recovering while the other gun can already accept work.
- A free gun side that is physically Recovering/PostShotRecovery is tracked as a future dispatch opportunity.
- If that side becomes plannable while another assignment is being materialized, the next planning round is triggered immediately; otherwise one temporary physical-recovery waiter keeps the event-driven retry alive.
- This preserves single-gun progress while still filling the second gun as soon as physical reality allows it.

- 当一门炮已经可以接任务、另一门空闲炮位仍处于 Recovering/PostShotRecovery 时，Pending 不再因为漏掉恢复事件而卡住。
- 处于物理恢复过程中的空闲炮位会被登记为后续调度机会。
- 如果它在另一项任务实体化期间已经恢复为可规划状态，系统会立即开启下一轮匹配；否则保留一个临时物理恢复等待器继续事件驱动重试。
- 因此单炮可以先继续执行，第二门炮一旦真正恢复可用就会立即继续承接 Pending。

### Release cleanup / 发版清理

- Removed the temporary aiming-speed, physical-state timeline, and trigger-console pose probes used during development validation.
- Normal categorized/problem diagnostics remain available through the existing diagnostics system.
- The single-plan order reason now reports that no immediately available partner FirePlan exists instead of incorrectly saying the Pending queue is empty.

- 移除了开发验证阶段使用的瞄准速度探针、物理状态时间线探针和 Trigger Console 姿态探针。
- 原有 diagnostics 系统的常规分类日志和 problems 日志仍然保留。
- 单计划执行时的射击顺序原因改为“当前没有可立即形成配对的计划”，不再错误显示“等待队列为空”。

### Notes / 说明

- F9 still discards reloadable TaskSystem planning/execution state while preserving physical loading transactions already accepted by the stable Host.
- Physical gun/loading state remains authoritative; the mod does not rewrite already accepted loading reality to match a new task.
- The shared firing lever remains a physical shared control. The automation coordinates Review/Arm work, while actual observed gunfire determines which plans are consumed.

- F9 仍然只丢弃可热重载 TaskSystem 的规划/执行状态；已经由稳定 Host 接受的物理装填事务继续保留。
- 实际炮膛与装填机构状态仍然是权威状态；系统不会为了新任务去虚构或覆盖已经发生的装填现实。
- 击发扳机仍然是共享物理控制；自动化负责协调 Review/保险流程，最终由实际观察到的物理击发决定消费哪些计划。
